# Migration guide 3.11.0 → 3.12.0

This template is consumed by copy. `lt fullstack update` does not sync the CI files or
`scripts/`, so nothing below reaches an existing project on its own — the pipelines and the
guard scripts are yours to copy by hand. Each section says what breaks if you adopt only
half of it.

---

## 1. The script-existence rule now covers `--filter` calls, in both directions

`scripts/check-ci-consistency.mjs` rule 7 asserts that a script a pipeline calls exists in
the package it targets. It previously skipped every `pnpm --filter … run <script>` call as
unverifiable. It now resolves a plain package **name** through the `packages:` globs in
`pnpm-workspace.yaml` and checks the script against that package.

The direction that matters more is the reverse one. A `--filter` naming a package the
workspace does **not** define is now a **failure**:

```
gitlab/build: `--filter app` names a workspace package
  no workspace package is named `app` — pnpm matches nothing, exits 0, and `build`
  silently never runs (workspace defines: api, @acme/app)
```

That is not a style rule. pnpm answers an unmatched filter by doing nothing and exiting 0,
which is how `pnpm --filter app` once let `nuxt build` never run and shipped an image built
from whatever `.output` the build context happened to carry — misdiagnosed as a BuildKit
cache bug for a while. The postmortem is in `.gitlab-ci.yml`'s `turboops-build` header and
in `.github/workflows/deploy.yml`.

**What to expect when you adopt the script:** if any pipeline job filters on a package name
that does not exist, `pnpm run check` goes red where it was green yesterday. That finding is
real — fix the filter or the package name, do not silence the rule.

`pnpm -r` and the set-valued filter forms (`api...`, `[origin/main]`, `!api`, a path) have no
single target. They are recorded as **skipped** and printed with the verdict, rather than
dropped silently:

```
[ci-consistency] ok — 22 rule(s) hold, 6 skipped: …
```

A quiet skip is how a guard comes to read as "held" in the one repo that owns these CI
files, which is exactly the repo where it cannot fire.

## 2. Workspace discovery is shared, and now sees symlinked members

New file: `scripts/lib/workspace-packages.mjs`, with `scripts/lib/workspace-packages.test.mjs`.

The same `pnpm-workspace.yaml` parse had been copied into `check.mjs`,
`check-workspace-consistency.mjs` and `check-ci-consistency.mjs`, and the copies had already
drifted — each resolving nothing under a slightly different but perfectly valid workspace
file, and each then reporting that every rule held.

Two behaviour changes come out of consolidating them, and both **widen** what the guards see:

- **Symlinked members count.** `lt fullstack init --api-link` / `--frontend-link` make
  `projects/api` / `projects/app` symlinks into your own checkout of the starter.
  `Dirent.isDirectory()` reflects an lstat and is `false` for a symlink, so filtering on it
  alone made every link-mode workspace look **empty** — to all three guards at once. If you
  work in link mode, these guards were not running for you; they are now.
- **More spellings of `packages:` are accepted** — a block list whose dashes sit at column 0,
  the flow form `packages: ['projects/*']`, and a comment on the key or between entries.
  Each of those made at least one copy resolve nothing.

**Adopt all four files together.** Copying `check-ci-consistency.mjs` without
`scripts/lib/workspace-packages.mjs` fails at import.

## 3. `peers` was missing from the parser's pnpm-subcommand list

`PM_SUBCOMMANDS` in `check-ci-consistency.mjs` tells the parser which bare `pnpm <word>`
calls are subcommands rather than script names. `peers` was absent while `pnpm peers check`
was being added to the check chains, so a pipeline that inlined that command was read as
`pnpm run peers` and the guard demanded a `peers` script — a fabricated failure on a correct
pipeline, in the `lint` job that `app:test` depends on through `needs:`.

The set is now audited against `pnpm help -a` (11.14.0). `test`, `start`, `t` and `c` stay
out deliberately: `pnpm test` really does run the `test` script, so checking that it exists
is the right behaviour.

## 4. `--filter-prod` is no longer blamed on the workspace root

An anchored `--filter[= ]` match does not match `--filter-prod`, which is a real pnpm flag,
so such calls fell through and were attributed to the workspace root — inventing a finding
on a correct pipeline. Any other `--filter*` spelling now stays unresolved, and `-F` (the
documented shorthand) is resolved like `--filter`.

Also fixed: a call carrying several `--filter` flags is checked in **each** filtered package.
pnpm runs the script in all of them; reading only the first let a missing script in the
second through while the guard reported success.

## 5. Two dependency gates joined the check chain — and the CI jobs

```jsonc
"check:peers":     "pnpm peers check",              // pnpm 11 builtin
"check:overrides": "node scripts/check-overrides.mjs"
```

Both run in `check:raw`, `check:fix` and `check:naf`, directly after `pnpm audit`, and both
were added to the `audit` job in **both** pipelines.

That last part is the half not to skip. The `audit` job's own comment claims it "matches the
local `pnpm run check` exactly — with no threshold gap between them", and a gate that fires
only on a developer's machine is precisely such a gap: the regression passes the MR and reds
whoever pulls next.

- **`check:peers`** requires **pnpm ≥ 11** (this template pins `pnpm@11.14.0` via
  `packageManager`; the subcommand exists across the whole `engines.pnpm: ^11.0.0` range).
  If your project is still on pnpm 10, raise pnpm before adopting this line — it is a hard
  failure otherwise. It asks whether the resolved tree is internally consistent, which
  `pnpm audit` does not; it matters because `autoInstallPeers: true` fills a missing peer
  silently. There is no `ignoreGhsas`-style escape hatch for an accepted peer warning, so
  fix the declaration rather than suppressing the step.
- **`check:overrides`** reports only advisories that land on a package which **already has**
  an override — the case `pnpm audit` cannot express. An override that exists but targets a
  version below the advisory's fix line looks like a solved problem and closes nothing; in
  one derived project nine of twelve declared overrides were in that state. It needs the
  network and degrades to a `WARN` on stderr plus `exit 0` when there is none, rather than
  passing silently.

None of the base repos declares any `overrides`, so nothing broken is inherited — the gate
is there for the projects generated from this template, which do.
