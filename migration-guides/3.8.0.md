# Migrating an existing project to lt-monorepo 3.8.0

This template is consumed by copy: a project generated from 3.7.x does **not**
pick these changes up automatically. Nothing here is required — but item 1 is a
**breaking change** for anyone who copies `.gitlab-ci.yml` forward without the
rest, so read that one even if you adopt nothing else.

Adopt in the order below; each step is independent and verifiable on its own.

---

## 1. The audit gate now blocks (BREAKING if adopted partially)

**What changed.** The CI `audit` job lost `allow_failure: true` (GitLab) and
`continue-on-error: true` (GitHub). Advisories that genuinely cannot be fixed now
live in `auditConfig.ignoreGhsas` in `pnpm-workspace.yaml`, one entry each with a
written rationale.

**Why.** The old flag suppressed *every* advisory, including ones published after
it was added. A genuinely new finding was invisible in a merge request and shipped
to production unseen.

**The trap.** If you copy the CI file forward but not the `auditConfig` block, you
get the blocking gate **without** the allowlist and your very first pipeline is red
on an advisory that was already assessed here. `auditConfig` was also **not** hoisted
by `lt fullstack init` at the time of this release (the hoist whitelist then covered
`overrides`, `allowBuilds`, `onlyBuiltDependencies`, `ignoredOptionalDependencies`,
`minimumReleaseAgeExclude`), so a freshly generated project had the same gap.

> **Update 2026-08-22:** lt CLI 1.42.0 (2026-07-31) added `auditConfig` to the hoist
> whitelist, so a generated project no longer has that gap — the suppressions now
> travel, and apply workspace-wide. Copying the CI file forward into an *existing*
> repo still needs the block copied with it.

**How to adopt.**

1. Run `pnpm audit` locally first and resolve what you can via `overrides:` — a pin
   to a patched version always beats an ignore entry.
2. For whatever remains, add an `auditConfig.ignoreGhsas` entry per advisory with
   all four required elements (advisory ID / why it is there / residual risk / date).
   See `pnpm-workspace.yaml` in this template for the format and the rules.
3. Only then remove `allow_failure` / `continue-on-error`.

Verify: `pnpm audit` exits 0 locally, and the CI audit job is green.

## 2. E2E runs against pre-built artifacts, in two shards

**What changed.** A `build` job compiles both projects and publishes
`projects/api/dist` + `projects/app/.output` as an artifact. `app:test` consumes it,
runs the **compiled** API (`start:e2e:dist`, with `migrate:up` before it) and lets
Playwright serve the **built** Nuxt server (`E2E_BUILT_SERVER=true`), split across
two shards. A follow-up job merges the shard reports into one HTML report.

**Why.** The suite was hitting the one-hour job limit without ever printing a
summary. `nuxt dev` recompiled every route on first hit and the API ran under
ts-node; both are now compiled once.

**Prerequisites — check these before adopting:**

- `projects/app` must be on a `nuxt-base-starter` whose `playwright.config.ts`
  honours `E2E_BUILT_SERVER` (it selects `node .output/server/index.mjs` over
  `nuxt dev`). Older starters ignore the variable and silently keep using the dev
  server — you get the sharding but none of the speedup.
- `projects/api` must provide `start:e2e:dist` and `migrate:up`.
- The `build` job must run on a **glibc** image (`node:22-bookworm-slim`, not
  `node:22-alpine`) if the E2E job uses the `playwright:*-noble` image. Nitro
  bundles platform-specific native binaries (`@img/sharp-*`) into `.output`; built
  on musl they cannot load on glibc, and because `ipx` imports sharp lazily the
  failure only appears on the first `/_ipx/**` request.

**Shard count.** Two, not four. Playwright shards per test, but a
`test.describe.serial` block is atomic — the 9-step auth-lifecycle chain is the
floor. Measured on the reference suite: `13/12` at two shards versus `7/6/11/1` at
four, so the extra containers buy the runtime of a single `goto('.')`. Raise it only
after that chain is split into independent groups.

> **New invariant:** any stateful spec must use `test.describe.serial`. Without it
> Playwright scatters its steps across shards, the dependent ones hit their own
> `test.skip(...)` guards, and the suite reports **green** having verified nothing.

Verify: the pipeline is green and produces one merged Playwright report.

## 3. `NUXT_BUILD_DIR=.nuxt-check` on the check chain

**What changed.** `pnpm run check` pins its package-manager invocations to an
isolated Nuxt build dir, so a check can no longer rewrite the `.nuxt/` a parked
`nuxt dev` is reading.

**Why.** `postinstall: nuxt prepare` inherits the env of whatever triggered the
install, and the check triggers one on every run. Unpinned, it rewrote
`.nuxt/tsconfig.json` under a running dev server, which then type-checked without
the `~`/`#` aliases and failed with a flood of TS2307 on perfectly fine code.

**Prerequisite.** Inert unless `projects/app` is on a starter whose `package.json`
already pins `.nuxt-check` in `build:check` / `typecheck:*`. Older starters need
that first, otherwise the check writes both directories and you gain nothing.

**Also add:** `.nuxt-check` to `projects/app/.gitignore`, and `**/.nuxt-check` to
the **root** `.dockerignore` (Docker never reads `projects/app/.dockerignore` for a
root-context build).

Verify: run `pnpm run check` while `lt dev up` is running — the dev server keeps
working, and a `.nuxt-check/` appears next to `.nuxt/`.

## 4. Wider `.dockerignore`, and it is now load-bearing

**What changed.** Added `projects/*/.npmrc`, `**/.nuxt-check`, `**/.nuxt-test`,
`**/.output-test`, `**/.nitro`, `**/.cache`, `**/.lt-dev`, `projects/api/uploads`,
`**/blob-report`, `**/*.log.*`, `**/*.swp`, `**/*.swo`, and widened the `.env`
family to `**/.env*`.

**Why it is load-bearing now.** The new `build` job publishes `.output` as an
artifact, and GitLab hands artifacts to later-stage jobs by default — so a build
output can land in the workspace where `docker compose build` runs with
`context: .`. `**/.output` and `**/dist` are what keep it out of the image. The
deploy jobs additionally carry `dependencies: []` as a second layer. **Do not
remove either without the other.**

**Note on anchoring.** `projects/api/uploads` is anchored on purpose. A bare
`**/uploads` matches any directory of that name at any depth, including application
source — a Nuxt route `app/pages/uploads/` would vanish from the build context and
the page would simply not exist in the image.

Verify: `docker compose build api app` succeeds and the images do not contain a
stale `.output`.

## 5. New guard: `scripts/check-ci-consistency.mjs`

Copy the script and wire `"check:ci": "node scripts/check-ci-consistency.mjs"` into
your `check:raw` / `check:fix` / `check:naf` chains and into the CI `lint` job.

It asserts only things that otherwise fail **silently green**: sharding without
`--shard`, a `$CI_NODE_INDEX`-gated step in a non-parallel job, a non-blocking audit
job, `E2E_BUILT_SERVER` without the build artifact wired in, and `start:e2e:dist`
without `migrate:up`. It no-ops cleanly when a rule matches no job, and says so
rather than reporting a silent pass.

Verify: `node scripts/check-ci-consistency.mjs` prints the list of rules it holds.
