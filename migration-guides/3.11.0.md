# Migrating an existing project to lt-monorepo 3.11.0

This template is consumed by copy: a project generated from an earlier version
does **not** pick these changes up automatically, and `lt fullstack update` does
not sync CI files — it heals the vendored CLAUDE.md blocks, `scripts/check.mjs`
and its import closure, and the migrate store. The CI pipelines and
`scripts/check-ci-consistency.mjs` are yours to copy by hand.

Item 1 is **breaking if adopted partially**, in both directions: the new guard
rule and the CI change it demands live in different files, and either one without
the other leaves you red — the script alone reds your first local
`pnpm run check`, the CI change alone leaves the defect unguarded.

**You are affected if you adopted [3.9.0](./3.9.0.md) §1.** That step told you to
move Mongo off loopback onto its service alias, which is precisely what triggers
this problem. If your `app:test` shards are red on `Refusing to delete test data`,
this is the guide.

---

## 1. An E2E job on a non-loopback database must be granted the reset permission (BREAKING if adopted partially)

**What changed.** Both `app:test` jobs — GitLab **and** GitHub Actions — now set
`E2E_ALLOW_REMOTE_DB: "true"`, and `scripts/check-ci-consistency.mjs` gained a
rule that asserts the pairing in both directions.

**Why.** The two halves of this contradiction live in different repositories, and
neither can see the other:

- `assertSafeToDelete` (in your project: `projects/app/tests/e2e/helpers/auth-backend.ts`)
  refuses to reset test data unless the database URI is on loopback or
  `E2E_ALLOW_REMOTE_DB=true`. It is a guard against a stray run emptying a real
  database, and it is right to exist.
- The `FF_NETWORK_PER_BUILD` rule from 3.9.0 **requires** addressing the mongo
  service by its alias — and an alias is not loopback.

So obeying one rule is what trips the other. The URI is set in your CI file, the
guard runs in your app's test helpers, and a local run never reproduces it because
locally the URI *is* `127.0.0.1`. The symptom is both shards failing on
`Refusing to delete test data: MONGO_URI is not loopback (mongodb://mongo:27017/...)`
while `pnpm run test:e2e` is green on your machine.

**On GitHub this also stops your deploy.** `deploy.yml` runs the test workflow as
its gate (`build-push: needs: [guard, test]`), so red shards mean no image and no
deployment — not just a red badge.

**The trap, and it has two jaws.** Copy the guard script without the CI change and
your first local `pnpm run check` is red on a rule whose fix lives in a file you
did not copy. Copy the CI change without the script and you have fixed today's
pipeline while nothing stops the next job from repeating it.

**Why the flag is safe here, and when it is not.** It is job-scoped on purpose. At
pipeline level it would hand a wipe permission to every job, including ones that
reset nothing. Set it only where the database is a per-job **service container**
that is destroyed with the job. Do **not** set it for a URI that could reach a
database outliving the run — that is the case the guard exists for. The second
half of the new rule enforces exactly this: a job carrying the flag must point at
a host it declares a `services:` entry for.

**How to adopt.**

1. Add `E2E_ALLOW_REMOTE_DB` to the job that runs the Playwright suite, in **each**
   pipeline you use.

   `.gitlab-ci.yml`, in `app:test`'s `variables:`:

   ```yaml
   E2E_ALLOW_REMOTE_DB: "true"
   ```

   `.github/workflows/test.yml`, in `app-test`'s `env:`:

   ```yaml
   E2E_ALLOW_REMOTE_DB: 'true'
   ```

   Do **not** put it in the global `variables:` / workflow-level `env:` block. The
   rule accepts it there, but it grants the permission far wider than needed.

2. Leave `api:test` alone. It declares a mongo service and a non-loopback URI too,
   but it runs the API suite, never Playwright, and so never calls
   `resetTestData`. The rule deliberately does not arm there — if you add the flag
   anyway you have widened a destructive opt-out for nothing.

3. Only then copy the updated `scripts/check-ci-consistency.mjs` and
   `scripts/check-ci-consistency.test.mjs`.

**Applies to BOTH pipelines**, unlike the `FF_NETWORK_PER_BUILD` rule. That one is
GitLab-only because GitHub gives every job its own ephemeral runner. This one is
not: our GitHub `app-test` runs inside `container:`, and a service container is
reachable from inside a job container only by its alias — never on `127.0.0.1`,
which GitHub maps only for jobs running directly on the runner. So the GitHub job
has the identical problem, not the absence of it.

> If your own GitHub job runs `runs-on: ubuntu-latest` **without** a `container:`
> and maps the service port (`ports: - 27017:27017`), then `mongodb://127.0.0.1:27017/...`
> is the correct address there and you need no flag. Loopback is loopback; the
> rule stays silent. Check which shape your job has before copying.

Verify: `node scripts/check-ci-consistency.mjs` lists both

```
gitlab/app:test: E2E data reset is permitted against the CI database
gitlab/app:test: the E2E reset opt-out targets a throwaway service container
```

plus the `github/test.yml/app-test:` equivalents if you use GitHub Actions. A rule
that is *absent* from that list did not pass — it never ran, which is the failure
mode this script exists to prevent.

## 2. The loopback pattern is now mirrored verbatim, with a drift detector

**What changed.** The checker's notion of "loopback" is now a character-for-character
copy of `LOOPBACK_URI` in the app's E2E helpers, and
`scripts/check-ci-consistency.test.mjs` gained a detector that compares the two.

**Why.** The first version paraphrased the pattern, and a paraphrase drifts both
ways — both of them bad:

- **Narrower** than the guard: `mongodb://localhost` (no port), `mongodb+srv://…`
  and `mongodb://user:pw@127.0.0.1/db` are loopback to the runtime guard but were
  not to the checker. The check then reds a pipeline that is perfectly correct,
  and the cheapest way out of a red check is to set the destructive opt-out that
  was never needed.
- **Wider** than the guard: `mongodb://127.0.0.1:27017,prod.example.com:27017/app`
  passed as loopback because the pattern stopped at the port colon, while the
  runtime guard refuses the seed list. Check green, CI red, a real host in the URI.

**How to adopt.** Nothing, if you copy both script files in step 1.3 — the mirror
and its detector travel together.

**Note for CI.** The detector needs a sibling `nuxt-base-starter` checkout to
compare against. Where that is absent it reports as **skipped**, never as passed —
a detector that silently "passes" without running is indistinguishable from one
that works. Set `LT_DRIFT_STRICT=1` in a workflow that does check out the sibling
(a release job) to turn absence into a hard failure.

---

## 3. Rules no longer report against non-job blocks

**What changed.** Top-level `.gitlab-ci.yml` keys that are configuration rather
than jobs — `variables`, `stages`, `default`, `include`, `workflow` — are no longer
valid subjects for the job rules.

**Why.** A pipeline that put `$CI_NODE_INDEX` in its global `variables:` block (a
per-shard database name is the obvious reason to) got a finding against
`gitlab/variables` — a "job" no runner executes and nobody can go and fix — while
the actual parallel job went unmentioned. Global values still reach every job as
inherited configuration, which is where they belong.

**How to adopt.** Nothing beyond copying the script. If you were carrying a
suppression or a puzzled comment about a `gitlab/variables` finding, you can drop
it.

Verify: `node scripts/check-ci-consistency.mjs` names only real jobs.
