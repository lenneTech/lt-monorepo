# Migration guide 3.18.3 → 3.18.4

This template is consumed by copy. `lt fullstack update` does not sync the CI files or
`scripts/`, so nothing below reaches an existing project on its own. Section 1 is a security
fix: apply it to every project that has a `turboops-build` job.

---

## 1. `turboops-build` runs on its own network

**What was wrong.** The pipeline sets `DOCKER_TLS_CERTDIR: ""`, so the `docker:29-dind` service
of `turboops-build` accepts connections on tcp 2375 without TLS or authentication. The job did
not set `FF_NETWORK_PER_BUILD`, so the runner attached that service to the runner host's shared
default bridge. Any container running on the same host at the same time, such as another
project's CI job on a shared runner, could reach `tcp://<dind-IP>:2375` and control the daemon
that builds and pushes your production images. It could replace an image between
`docker compose build` and `docker compose push`.

**Am I affected?** Yes, if a job in your `.gitlab-ci.yml` has a `dind` service and neither the
job, a block it extends, nor the global `variables:` sets `FF_NETWORK_PER_BUILD: "true"`.
Every project created from this template before 3.18.4 is affected:

```bash
grep -n "dind\|FF_NETWORK_PER_BUILD" .gitlab-ci.yml
```

**Fix.** Add the flag to the job:

```yaml
turboops-build:
  stage: turboops-build
  image: docker:29-dind
  services:
    - docker:29-dind
  variables:
    FF_NETWORK_PER_BUILD: "true"
```

The job itself does not change. Job variables are merged with the global ones, so
`DOCKER_TLS_CERTDIR: ""` still applies. The job still reaches the daemon as `docker`: the
image's entrypoint sets `DOCKER_HOST` to `tcp://docker:2375`, and on the per-build network
the service carries that hostname as its alias. `api:test` and `app:test` already run this way
for their `mongo` service.

One side effect concerns DNS inside the image build. On the per-build network the daemon
resolves names through Docker's embedded DNS server (`127.0.0.11`), which the `RUN` steps of
your Dockerfiles cannot reach. Docker therefore gives those steps the public resolvers
`8.8.8.8` and `8.8.4.4` instead of the runner host's resolver. If your runner host blocks
outbound DNS to public resolvers, `pnpm install` inside `docker compose build` fails after this
change. Allow outbound DNS to them on that host.

The flag only takes effect on the Docker executor, and a `network_mode` in the runner's
`config.toml` overrides it. If your runner sets one, the fix does not take effect. Ask
whoever operates the runner.

**How to verify.** The job only runs on `dev` and `main`, so the next push to `dev` is the
test: `turboops-build` must pass, and both images must be in the registry.

## 2. The CI guard enforces the flag

`scripts/check-ci-consistency.mjs` (rule 6) used to require `FF_NETWORK_PER_BUILD` only for
`mongo` services. It now also requires it for every Docker-in-Docker service. Copy the script
together with `scripts/check-ci-consistency.test.mjs`, because the new tests fail against the
old script.

If you copy the guard but skip the fix from section 1, `pnpm run check` fails:

```
gitlab/turboops-build: dind service requests per-build networking (docker executor):
  declares a Docker-in-Docker service but no `FF_NETWORK_PER_BUILD: "true"` …
```

That finding is real. Fix the job, not the rule.

## 3. Optional: TLS for the Docker daemon

After section 1, only the job's own containers can reach the daemon. TLS
(`DOCKER_TLS_CERTDIR: "/certs"`) adds a second line of defence for runners that ignore the
flag. **It cannot be enabled in the template alone.** The dind service writes the client
certificate to `/certs/client` inside its own container, and the job container only receives
it when the runner shares that directory between the two. Without that, the job finds no
certificate, falls back to `tcp://docker:2375` and fails with
`Cannot connect to the Docker daemon at tcp://docker:2375`.

Apply the changes in this order:

1. On **every** runner that runs the project's pipelines (Docker executor), add `/certs/client`
   to the existing `volumes` in `config.toml`:

   ```toml
   [[runners]]
     executor = "docker"
     [runners.docker]
       privileged = true                     # already required for dind
       volumes = ["/certs/client", "/cache"]
   ```

   GitLab Runner reloads `config.toml` without a restart.
2. Then set `DOCKER_TLS_CERTDIR: "/certs"` in `.gitlab-ci.yml`. The job image's entrypoint
   switches to `tcp://docker:2376` with `DOCKER_TLS_VERIFY=1` and
   `DOCKER_CERT_PATH=/certs/client` on its own. Nothing else in the job changes.

If you do it the other way round, every `turboops-build` run fails until the runner has the
volume. Keep `FF_NETWORK_PER_BUILD` either way.
