# Migrating an existing project to lt-monorepo 3.9.0

This template is consumed by copy: a project generated from 3.8.x does **not** pick
these changes up automatically. Item 1 is **breaking if adopted partially** — the
new guard rule and the fix it demands live in two different files, and copying one
without the other reds your very first local `pnpm run check`. Read that one even
if you adopt nothing else.

Adopt in the order below; each step is verifiable on its own.

---

## 1. Every job with a `mongo` service must set `FF_NETWORK_PER_BUILD` (BREAKING if adopted partially)

**What changed.** `api:test` now sets `FF_NETWORK_PER_BUILD: "true"` (`app:test`
already did), and `scripts/check-ci-consistency.mjs` gained a rule enforcing the
pairing for *every* GitLab job that declares a `mongo` service.

**Why.** Without the flag the runner leaves the service on the shared **default
bridge** in the deprecated `--link` mode instead of giving the build its own
network with DNS aliases. Two consequences:

- `mongo:7` runs without authentication, so on the default bridge every other
  container on that host can read and write your CI database. Port access is full
  access.
- Link-based alias resolution is the fragile path. When it goes, the job dies on
  `getaddrinfo ENOTFOUND mongo` — once per call, each preceded by MongoDB's 30 s
  server-selection timeout. The log reads like failing sign-up tests and the real
  cause sits thousands of lines up.

To be precise about the mechanism, because the first version of this change got it
wrong: service **containers** are per job either way — the runner never shares
those. What the flag changes is the **network** they sit on.

**The trap.** Copy the guard script forward without the CI file and your first
`pnpm run check` is red — locally, before CI ever runs — on a rule whose fix lives
in a file you did not copy.

**How to adopt.**

1. Add `FF_NETWORK_PER_BUILD: "true"` to the `variables:` block of **every** GitLab
   job that declares a `mongo` service. A single entry in the global `variables:`
   block also satisfies the rule, if you prefer it in one place.
2. **Check every such job addresses Mongo by its service alias**
   (`mongodb://mongo:27017/...`), not `127.0.0.1` / `localhost`. With a per-build
   network the service is no longer reachable on loopback. This is the one way
   step 1 can break a job that is green today.
3. Only then copy the updated `scripts/check-ci-consistency.mjs`.

**Not needed on GitHub Actions.** Every job there gets its own ephemeral runner
and its own service containers, torn down with the job — there is no shared bridge
to move off. The rule is GitLab-only for that reason.

**Runner caveat.** The flag is a *request*. It applies on the Docker executor only
(Kubernetes executors run services as pod sidecars; Shell executors have no service
containers), and a `network_mode` in the runner's `config.toml` overrides it. The
guard enforces that you ask; it cannot verify your runner complies.

Verify: `node scripts/check-ci-consistency.mjs` lists
`gitlab/<job>: mongo service requests per-build networking (docker executor)`
among the rules that hold.

## 2. Mongo watchdog around the Playwright run (recommended)

**What changed.** Both `app:test` jobs (GitLab and GitHub) now run Playwright
through `scripts/mongo-watchdog.sh`. It polls `mongo:27017` alongside the run and,
after 15 consecutive misses (~45 s), aborts with an explicit "CI INFRASTRUCTURE
fault" message plus a short forensics block and a guide for reading it.

**Why.** Item 1 removes the *cause*; a service container can still die mid-run.
Before the watchdog that cost ~95 s per remaining test (30 s server-selection
timeout × Playwright's `retries: 2`), i.e. ~19 min per shard spent verifying
nothing — with a log that looks like failing sign-up tests. The runner time matters
less than the diagnosis: nothing else in the stack distinguishes "the mongo
container died" from "the auth tests are broken".

**How to adopt.**

1. Copy `scripts/mongo-watchdog.sh` (keep the executable bit) and
   `scripts/mongo-watchdog.test.mjs`.
2. Add the test file to your `test:scripts` script.
3. Replace the bare Playwright invocation in your E2E job with:

   ```yaml
   - |
     cd projects/app
     WATCHDOG_API_URL="$API_URL/meta" \
       "$CI_PROJECT_DIR/scripts/mongo-watchdog.sh" mongo 27017 -- \
       pnpm exec playwright test --shard="$CI_NODE_INDEX/$CI_NODE_TOTAL" --reporter=blob
   ```

**Contract.** The watchdog never changes a verdict: a failing test run keeps its
own exit code, a green one stays green. It only converts a hang into a fast,
named failure. Both directions are pinned by the test file — do not drop it.

**Tunable via env:** `WATCHDOG_INTERVAL` (default 3 s), `WATCHDOG_MISSES`
(default 15), `WATCHDOG_KILL_GRACE` (default 5 s), `WATCHDOG_CONNECT_TIMEOUT`
(default 5 s), `CI_DEBUG_NETWORK=1` to include raw resolv.conf/address/route dumps
that are otherwise omitted (job logs are readable by anyone your project's
`public_builds` setting admits — default: on).

Verify: `node --test scripts/mongo-watchdog.test.mjs` passes, and a normal
pipeline shows no `WARN: mongo:27017 unreachable` lines.

## 3. `api:test` gained a timeout and a readiness wait (recommended)

**What changed.** `timeout: 30 minutes` on the job, and a
`until (exec 3<>/dev/tcp/mongo/27017)` wait before the suite, mirroring `app:test`.

**Why.** The job had no ceiling of its own: `vitest.config.ts` sets no `bail` and
no global run limit, and `globalSetup`/`globalTeardown` are **not** covered by
`hookTimeout` — so a hung setup ran until the instance-wide job timeout, typically
an hour. Adjust the value if your API suite is genuinely longer than 30 minutes.

Verify: the job is still green and its log shows the wait completing immediately.

---

## 4. `after_script` no longer prints the API log on green runs

**What changed.** The GitLab `app:test` `after_script` now checks
`$CI_JOB_STATUS` before tailing `$NEST_SERVER_LOG`.

**Why.** GitLab has no `if: failure()` for `after_script` — it runs on every
outcome. The comment claimed "on failure" while the tail landed in green jobs too.
That log carries the `[EMAIL VERIFICATION] … token=…` lines the specs parse; in a
project whose API is chattier at boot, correspondingly more. The GitHub twin
already gated on `if: failure()`.

Verify: a green pipeline's `app:test` job no longer ends with 60 lines of API log.
